# M4 — Promotion image + video frame

## Delivered scope

`/dashboard/frame` combines one ready promotion image and one ready clip from M2. The owner creates a draft, edits headline/CTA, chooses the starting second and 6/10/15-second duration, selects fit-to-show-all or centered crop-to-fill, and chooses whether to preserve source audio. Output is a 720×1280, 24 fps H.264 MP4 with AAC audio when enabled and present.

The top contains the original poster, shop name, optional logo and headline. The middle holds the selected clip segment. The footer displays the owner's CTA and selected contact/payment/trust information from the pinned Brand Kit revision. No price OCR, generated replacement graphics, fabricated claims, music, or paid AI calls are used. Layout is deterministic; copy remains owner editable. Image and clip uploads are reused unchanged in storage; the exported video necessarily resizes/re-encodes them.

The preview PNG is generated by the same `frameArtwork` function used by the worker. The browser places the source video in its transparent middle window. Fit and start/duration are shown for review; native playback controls are excluded from the export. Editing invalidates preview confirmation. The owner must refresh the preview and confirm one render credit before submitting. Unsubmitted form changes are not persisted across reloads; submitted plans and jobs are persisted.

## Shared backend

Apply `20260915_video_frame.sql` after M1–M3 before running the updated app or worker. The migration adds mode, clip reference and frame-plan fields to M3 jobs. Existing rows default to motion mode. Separate frame routes validate M4 input; M3 routes cannot submit frame jobs. Both modes use the same explicitly granted `motion_entitlements`, monthly video credit bucket, storage reservation, retry/lease fencing, orphan cleanup, output expiry and download authentication.

Frame drafts pin both owned assets and the shop's current immutable Brand Kit revision. Later brand edits do not alter prior frames. Inputs remain protected from deletion and expiry cleanup while their job is active. Frame rendering revalidates actual clip duration. Out-of-range selections, foreign assets, missing/unconfirmed trust statements and payment/contact selections absent from the pinned profile are rejected. The server resolves brand values; client-supplied payment names or trust text cannot override them.

The shared asset endpoint supports authenticated single byte ranges for `?inline=1` video playback. It returns 206 for valid ranges, 416 for malformed/out-of-bounds ranges, and still verifies ownership/readiness/expiry. Private Blob streaming currently reads/discards preceding bytes for a ranged request; staging should assess storage egress for long clips. Normal attachment downloads keep existing behavior.

## Rendering and hosting

The external media worker needs FFmpeg/libx264/AAC, ffprobe and a Thai-capable font. Set `FRAME_FONT_PATH` on both web and worker hosts to the same installed font file; Windows defaults to `C:/Windows/Fonts/tahoma.ttf`. No font file was copied into the repository. Preview and rendering use Sharp/Pango with escaped text; no user text becomes FFmpeg filter syntax or executable code. Brand colors are hex validated. Files use generated temporary directories; renderer subprocesses have timeouts, bounded logs and file-only input protocols.

M4 renders for at most 15 seconds and shares the 32 MiB output reservation. Missing audio is allowed; audio disabled produces a silent output. No worker server was provisioned, no live database was migrated and no production deployment was made. The private Blob integration, hosted Thai font rendering and worker capacity still require staging verification. No new subscription plan benefits were enabled by the migration.
